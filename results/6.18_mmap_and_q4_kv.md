# 方向 1（前段 mmap 載入）與方向 2（KV q4_0）：容量、速度與精度（31B，兩板，切點 33）

**結論：**
1. **KV 改成 q4_0，容量約變成 1.9 倍**：兩板管線每人 1K / 4K / 8K / 32K 可服務 **97 / 77 / 61 / 27 人**（q8_0 為 51 / 41 / 32 / 14）。資料平行（兩板）也跟著變成 40 / 30 / 22 / 10 人，管線仍是它的 2.4–2.8 倍。容量仍受前段限制（後段可到 133 / 102 / 78 / 32）。
2. **但 q4_0 讓長對話慢約 5%，精度也明顯下降**：每人各自 4K 時，8 人 9.76 → 9.28、16 人 10.75 → 10.15 t/s；填入開頭慢 7%。和 f16 標準答案比較，61 列中 57 列 top-1 相同（q8_0 為 60/61），最大 logit 差 5.85（q8_0 為 1.13）。原本預期「KV 變小、讀得更快」不成立：長對話的瓶頸是計算，q4_0 還原數值的成本比省下的讀取量更大【推測】。
3. **前段用 mmap 載入，容量多 10–14%**（swappiness 10）：q8_0 每人 4K 41 → 45 人，q4_0 77 → 85 人。載入後可用記憶體多 1.4 GB，剛好是詞嵌入表（`token_embd`，q8_0，1.4 GiB）：dio 會把整張表讀進記憶體，mmap 只讀入實際用到的列。swap 只增加 27–48 MB，沒有被監控程式停止（`6.13` 在 swappiness 100 時失敗）。代價：載入時間 293 → 516 s（+76%）。
4. **建議**：預設維持 q8_0 + dio。需要服務的人數超過 q8_0 容量時，再改用 q4_0（並先確認精度可以接受）；mmap 等接近容量上限時實際跑過管線、確認速度沒有變慢後再採用。

- mmap 時，權重先映射成檔案頁（8.7 GB），重排（`q4_0_4x8`）後再複製一份到一般記憶體；原本的檔案頁不會再被讀取，但仍留在記憶體裡，直到系統需要空間才丟掉。

- 唯一還會被讀取的檔案頁是詞嵌入表中用到的列，每 token 一列（約 5.7 KB），量很小。

## 解讀
1. **容量方面 q4_0 的效果很清楚**：每人 KV 從約 325 降到 174 MiB（4K），人數接近加倍。管線對資料平行的倍數（2.4–2.8 倍）維持不變，因為兩邊同樣受益。
2. **速度與精度是 q4_0 的代價**：
   - 長對話慢約 5%。q8_0 曾經讓長對話變快（`6.13`，比 f16 快 10–44%），但 q4_0 沒有再變快，代表瓶頸已經從「讀取 KV」轉移到「計算」。前段 99% 忙碌也符合這點【推測】。驗證方式：用 `llama-batched-bench` 單板比較 f16 / q8_0 / q4_0 在 4K 上下文時的每步時間。
   - 精度：61 列中 4 列 top-1 不同，最大差 5.85。對實際生成品質的影響需要再評估（例如比較一段較長的生成文字，或量 perplexity）。
3. **mmap 的收益來自詞嵌入表**：前段只需要查表，用不到整張表；dio 卻會把 1.4 GiB 全部讀進來。mmap 讓它按需讀取，省下 1.4 GB，對前段（容量瓶頸）約多 10% 的人數。更乾淨的做法是：權重用 dio 載入、只有詞嵌入表用 mmap，這樣既省 1.4 GB，載入時間也不會變長（需要改 llama.cpp 載入程式，約半天）。
4. **mmap 尚未在接近容量上限時實際跑過管線**：`llama-cap-test` 每個人數只解碼 1 個 token。長時間運作時，若系統把詞嵌入表的頁面丟掉再讀回，速度可能會下降（推測影響很小，因為每個 token 只讀一列）。
