# 切點 33 / 34 / 35：短對話吞吐與容量（31B，兩板）

**結論：**
1. **把切點往後移，短對話吞吐可再提高約 3%**。32 人：33 層 24.76–24.88 → 34 層 25.43 → 35 層 25.56 t/s；64 人：24.94 → 25.66 → 25.74 t/s。在 34 到 35 之間已經接近平衡，35 只比 34 再快 0.3–0.5%。
2. **瓶頸在 34 到 35 之間換邊**：忙碌比例（前 / 後）33 層 90% / 99%，34 層 95–96% / 98%，35 層 98% / 96%。再往後移只會換成前段變成瓶頸。
3. **容量受前段限制，切點往後移會讓容量略降**：q8_0 每人 1K / 4K / 8K / 32K，33 層 51 / 41 / 32 / 14 人，34 層 49 / 39 / 31 / 14 人（−0 到 −5%）；f16 是 27 / 21 / 17 / 7 → 26 / 20 / 16 / 7 人。
4. **建議預設切點改為 34**：短對話吞吐 +2.5–2.9%，容量只少 1–2 人（約 −4%）。若最重視容量，就維持 33。35 只比 34 快 0.3–0.5%，但前段變成瓶頸，容量會再少一些（推測，35 層的容量未量測）。
5. 正確性：34、35 層的 61 列驗證都是 PASS（top-1 61/61，最大差 0），序列 0 生成的 32 個 token 都與標準答案相同。

## 解讀
1. **短對話的瓶頸是兩段裡較慢的那一段**。切點 33 時後段多做了約 1.5 層的工作；移到 34 後兩段幾乎平衡，35 則換前段變慢。吞吐的峰值約 25.7 t/s，在 34–35 層之間。
2. **長對話要另外看**【推測】：長對話時每層讀 KV 的成本與層的種類有關（第 5、11…59 層是完整注意力），兩段的平衡點可能跟短對話不同。`6.13` 中切點 33、各自 4K 開頭、32 人時忙碌為 98% / 98%，已經平衡，所以長對話移到 34 不一定更快。驗證方式：`pp_run.sh` 切點 34 跑 `--prefix 4000 --distinct --kv-type q8_0 --configs 16x2,32x2`，與 `6.13` 的 10.73 / 12.98 t/s 比較。
3. **吞吐和容量是取捨關係**：前段同時放詞嵌入表，記憶體本來就比較緊，切點往後移，前段的權重和 KV 都會增加。兩者的差距都在 5% 以內，對專題的主要結論（管線與資料平行吞吐持平、容量多 2.4–3.5 倍）沒有影響。
4. 4 板時每段約 15 層，可以用同樣的方法（看忙碌比例）調整切點。
