# 跨板管線平行：31B 拆成兩段，分別跑在 node1 + node2

**結論：Gemma 31B 拆成兩段、跨兩張板子執行，輸出與單板完整模型逐位元相同；每個 token 的網路往返只要 1 ms（佔 0.2%）；每張板子只用 9.4 GB，各自剩下約 15 GB 可給 KV Cache。** 目前一次只處理一個請求（B=1），尚未把兩段的運算重疊起來，所以吞吐量和單板相同。下一步是讓多個請求在兩段之間流水進行。

## 架構
- **node1（前段 / Stage 0）**：第 0–30 層加上 `token_embd`。負責 tokenize、執行前段，再把隱藏狀態（fp32，n_tokens × 5376）傳給 node2。
- **node2（後段 / Stage 1）**：第 30–60 層加上 LM Head（與 `token_embd` 共用權重）。接收隱藏狀態、執行後段，回傳 logits（驗證模式）或 argmax token（測速模式）。
- **傳輸**：TCP（`TCP_NODELAY`），走 5G 直連 `10.0.0.1 → 10.0.0.2:9000`。自訂二進位標頭：magic、type、n_tokens、pos0、n_embd、want_logits。
- **程式**：`llama-pp-stage`（新），建立在 `pp-layer-range` 的層範圍功能上。原始碼在 `results/patches/pp-stage/`，兩張板子都放在 `~/llama.cpp-pp/tools/pp-stage/`。
- **準備工作**：
  - node2 建立同樣的 `~/llama.cpp-pp` worktree（branch `pp-layer-range`），套用 `results/patches/pp-layer-range.patch`，並用標準參數編出 `build-pp`（`armv8.6-a+dotprod+fp16+i8mm`）。
  - 31B GGUF 經 5G 直連從 node1 複製到 node2：17 分鐘，速度受 USB 隨身碟寫入限制。兩邊 SHA-256 相同（`031dc1c5…dcd834`）。
  - 為此在 node2 刪除了 Qwen2.5-7B（4.4 GB）與誤建的 `~` 資料夾（dllama 舊模型，1.7 GB），經使用者同意。

## 解讀
1. **跨板切層正確**：隱藏狀態經 TCP 傳輸（fp32，沒有轉換）不影響結果，輸出與單板完全相同。
2. **網路成本可以忽略**【實測】：每個 token 往返 1.0 ms，佔 0.2%；prefill 29 token 為 2.1 ms。5G 直連完全不是瓶頸。
3. **跨板比同程序慢約 6%**【推測】：
   - 前段多 0.012 s、後段多 0.014 s，網路只佔 0.001 s，所以變慢的是運算本身。
   - 可能原因是兩張板子都在 `schedutil`：每個 token 都要等另一段算完，空檔中 CPU 會降頻，下一步再爬升回來。單板同程序時，兩段是連續執行的。
   - 驗證方法：兩張板子切成 `performance` 後重測。
4. **這次吞吐量沒有提升是預期的**：一次只處理一個請求時，兩段是輪流工作的，每張板子約一半時間在等。要提升吞吐量，需要讓多個請求在兩段之間流水進行（企劃書 4.1）。
5. **記憶體優勢已經實現**【實測】：
   - 單板跑完整 31B，只剩約 6 GB 可給 KV。
   - 跨兩板後，每張板子剩 **15.2 GB**，約 2.5 倍，與企劃書 1.3 的估算方向一致（4 段時每板約 19 GB）。

## 下一步
1. 兩張板子切成 `performance` 後重測，確認第 3 點的推測。
2. **多請求流水線**：讓 node1 在 node2 計算的同時處理下一個請求或下一個 micro-batch。預期 2 段的吞吐量接近 2 倍（每段約 0.25 s，週期由較慢的後段決定）。
3. 批次（B>1）在跨板模式下的驗證，序列化格式是否要改成 fp16。
4. 依 6.6 的推算做非對稱切層（後段少分約 6 層），讓兩段時間相等。
