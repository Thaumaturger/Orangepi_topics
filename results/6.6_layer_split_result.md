### 記憶體與耗時（同一程序內兩段串接，非跨板）

| | 完整模型 | 第一段 [0, 15) | 第二段 [15, 30) |
| --- | --- | --- | --- |
| 程序記憶體（RSS） | 14,788 MiB | 7,621 MiB | 7,431 MiB |
| 權重（重排後 + 其他） | 13,882 + 792 MiB | 6,563 + 770 MiB（含 `token_embd`） | 7,319 + 22 MiB（含 LM Head） |
| KV cache（完整層 + SWA 層，n_ctx 1024） | 20 + 200 MiB | 8 + 104 MiB | 12 + 96 MiB |
| prefill 29 token | 0.64 s | 0.23 s | 0.42 s |
| 每個生成 token | 0.074 s（13.50 t/s） | 0.025 s | 0.049 s |

解讀：
- **記憶體真的分開了**：兩段相加等於完整模型，KV 也只配置在各段自己的層。
- **切開本身沒有額外成本**：兩段合計 13.54 t/s，與完整模型的 13.50 t/s 相同。這是同一程序內的結果，不含網路。
- **第二段的耗時是第一段的 2 倍**【推測】：兩段層數相同，差別在第二段多了 LM Head（262144 × 2816 的 Q8_0 矩陣乘法）和 softcapping。這直接支持企劃書 4.2 的非對稱切層：最後一段應少分幾層。
- **權重大小差異**：第一段的 `token_embd` 只用來查表，第二段的 LM Head 要做矩陣乘法。

## 開發過程中修正的問題
1. 驗證工具原本從只載入詞表的模型讀層數，但那種模式不提供層數。改成把層數和維度存在標準答案檔裡。
2. 第一次的 prompt 沒有套用對話格式，指令微調模型輸出重複的文字。改成 Gemma 4 對話格式後，輸出正常。
3. 中間段沒有用到「輸出列索引」這個輸入，導致它沒有配置記憶體，觸發斷言失敗（`GGML_ASSERT(buffer)`）。原因是完整模型在最後一層才挑輸出列，中間段到不了最後一層。改成中間段一律自己挑輸出列。

- 節點：node1，2026-11-10 16:02–16:21（板子時間，UTC），**調頻 `schedutil`**（對正確性無影響，下方耗時僅供參考），8 大核，`-lm dio`

- 完整模型的回答：通順（"Pipeline parallelism splits a large model into smaller segments, allowing each segment to be loaded onto a separate device's memory…"）

| 項目 | 結果 |
| --- | --- |
| 比對列數 | 61 列（prompt 29 + 生成 32） |
| 最高分 token 一致 | **61 / 61** |
| 下一個 token 一致 | **31 / 31** |
| logits 最大絕對誤差 | **0.000**（逐位元相同） |
| 判定 | **PASS** |

| | 完整模型 [0, 60) | 第一段 [0, 30) | 第二段 [30, 60) |
| --- | --- | --- | --- |
| 程序記憶體（RSS） | 18,680 MiB | 9,587 MiB | 9,376 MiB |
| 權重（CPU + 重排後） | 1,433 + 17,139 MiB | 1,431 + 7,855 MiB | 3 + 9,283 MiB |
| KV cache（完整層 + SWA 層，n_ctx 1024） | 80 + 800 MiB | 40 + 400 MiB | 40 + 400 MiB |
| prefill 29 token | 2.74 s | 1.20 s | 1.51 s |
| 每個生成 token | 0.471 s（2.12 t/s） | **0.215 s** | **0.257 s** |

兩段同時載入時，可用記憶體最低剩 4.9 GB，swap 全程 0，記憶體壓力 0。

解讀：
- **兩段的 KV 剛好相等**：從第 30 層切開，兩邊各有 5 個完整注意力層（第 5、11、17、23、29 層 vs. 第 35、41、47、53、59 層）。
- **第一段和第二段的權重一樣大（約 9.3 GB）**：第一段多了 `token_embd`（1.43 GB，只查表），第二段多了共用同一份權重的 LM Head（同為 1.43 GB，要做矩陣乘法）。
- **第二段每個 token 多花 0.042 s**：正好約等於用 36 GB/s 的頻寬把 1.43 GB 的 LM Head 讀一遍（約 0.040 s）【推算】。每層約 7.2 ms（0.215 s ÷ 30），所以 **LM Head 的成本約等於 6 層**。
- **對 4 段切層的建議（推算，待實測）**：
  - 最後一段少分約 6 層，才能讓各段的生成時間相等。
  - 第一段的 embedding 只查表，幾乎不花時間，但同樣佔 1.43 GB 記憶體。若以記憶體平衡為目標，第一段也要少分約 5–6 層（每層約 0.26 GB）。
  - 兩個目標在第一段有衝突，要依瓶頸是記憶體還是速度來選。
- **切開本身不增加成本**：兩段合計 2.12 t/s，與完整模型相同。這是同一程序內的結果，不含網路。
