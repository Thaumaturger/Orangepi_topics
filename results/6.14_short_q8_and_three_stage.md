# 短對話 32–64 人（f16 vs q8_0），以及三段管線的正確性驗證（31B）

**結論：**
1. **短對話時，32–64 人的總吞吐都停在約 24.9 t/s**（32 人 24.76、48 人 23.44、64 人 24.94 t/s）。人數再增加也不會更快：後段 99% 忙碌，已經是計算瓶頸。
2. **短對話時 q8_0 與 f16 完全一樣快**（24.63 / 23.34 / 24.94 t/s）。短對話的 KV 很小，讀 KV 不是瓶頸，所以 q8_0 在短對話只省記憶體，不影響速度。序列 0 生成的 32 個 token 也與標準答案完全相同。
3. **大批次時後段是瓶頸**（前段 90–93%、後段 99%），切點從第 33 層往後移到第 34 層，可能讓兩段更平衡。
4. **三段管線可以運作，而且與單板逐位元相同**：node1 [0,20) → node2 [20,40) → node2 [40,60)，61 列驗證 PASS，三個組態的 32 個生成 token 全部一致。`llama-pp-stage` 新增 `--role mid`，4 板時串成 first → mid → mid → last 即可。

## 結果【實測】

| 人數 | f16 | q8_0 | 每人（f16） | 忙碌 前 / 後 |
| --- | --- | --- | --- | --- |
| 32（每 micro-batch 16） | 24.76 | 24.63 | 0.774 | 90% / 99% |
| 48（24） | 23.44 | 23.34 | 0.488 | 93% / 99% |
| 64（32） | 24.94 | 24.94 | 0.390 | 91% / 99% |

先前（`6.10`）32x2 為 24.88 t/s，這次 24.76（相差 0.5%）。
記憶體最低可用：f16 前 6.3 GB / 後 9.4 GB；q8_0 前 10.0 GB / 後 12.4 GB。最高溫度 70–74°C。
q8_0 的驗證列：60/61 top-1 相同，最大 logit 差 1.13（與 `6.13` 相同）；生成的 token 與標準答案 32/32 相同。

## 解讀
1. **短對話的上限約 25 t/s 是後段的計算量決定的**：後段 99% 忙碌，加人只是讓每人變慢。要再提高總吞吐，可以：調整切點讓兩段平衡（第 34 層）、或增加板子（4 段時每段的層數減半）。
2. **q8_0 在短對話沒有代價**，在長對話有好處（`6.13`），所以之後一律用 q8_0 是合理的預設。
3. **三段的中段以獨立執行緒回傳結果**，不會阻塞下一批資料的計算。三段在兩板上的速度沒有意義（node2 的兩段各只用 4 核、而且共用記憶體頻寬），要等 node3 到位才能量真正的三段 / 四段速度。
4. 單一序列（1x1）時三段 2.06 t/s，兩段短對話是 2.10 t/s（`6.10`），多一次網路傳遞的成本很小（每 token 多約 0.01 s）。
